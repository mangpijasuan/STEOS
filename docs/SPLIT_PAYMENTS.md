# Manual split payments — Phase 5A

This branch is stacked on the Order Terminal branch (PR #41). It must be reviewed and tested after that branch; migration `0017_split_tenders.sql` follows `0016`. It does not charge a card or change Stripe, live settings, online checkout, pricing, fees or customer storefronts.

Staff can allocate an order total equally among 2–20 guests or enter custom cent amounts, using cash, a restaurant's own card terminal, or other tender for each part. Remaining/overallocated cents are visible in the dialog; no settlement is enabled until the total matches and staff explicitly confirm all listed payments have been received. The Order Terminal can settle when placing an order; an accepted, ready or completed in-person order can be settled from its receipt (linked by Split bill in the table sheet).

One settled payment row per order remains the reporting and refund authority. Each manual split has an immutable tenant-isolated breakdown of tender rows, linked to that payment using a composite foreign key. The existing order row lock makes the full settlement atomic; exact retry of the same order, recording staff member, key and tender list is safe. An alternative or competing payment cannot overpay the order. The till uses the existing order-request idempotency fingerprint, including the tender breakdown; an existing order uses its dedicated settlement endpoint. The whole payment plus all tenders commit or roll back together. Server validates current cents. No card data is entered or stored.

The receipt displays each allocation and can print a guest's payment receipt (not an itemized guest bill). Reports retain one sale and one fee per order; mixed method amounts are allocated from the breakdown and sum to the order's gross, while a mixed order is counted under each method it used. Existing full in-person refunds require staff to return all collected tender amounts externally and confirm the full refund. The tender breakdown remains as historical evidence; no automatic partial refunds or payment-provider calls are performed.

**Scope limitation:** This version records a complete split in one transaction only. It does not save partially collected payments across sessions. Do not collect part of a bill and leave this screen expecting the partial amount to be saved; settle only when all amounts have been collected. Durable partial collection, split refunds/voids, item-level bill allocation, separate itemized guest bills, and payment-terminal integration are subsequent phases. Never use actual cards in sandbox testing.
